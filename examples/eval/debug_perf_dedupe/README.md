## 改动内容

**1. 性能：O(n²) → O(n α(n))**
- 原来对每条记录都向后扫描所有记录（20 万条约 200 亿次比较）。
- 改为**并查集（union-find，含路径压缩 + 按秩合并）**：一次遍历，用两个哈希表记录每个规范化邮箱/电话首次出现的下标，再次出现时直接 `union`，把同邮箱/同电话的记录合并到同一集合。全程 O(n α(n))。

**2. 正确性**
- **传递性**：原代码只拿当前记录 `a` 与后续记录逐一比较，无法处理"A、B 邮箱相同，B、C 电话相同 ⇒ A、B、C 同组"的链式关系，这正是"同一个人的记录没被合并"的主因。并查集天然支持传递闭包。
- **邮箱去空白**：`normalize_email` 原来只有 `.lower()`，没实现文档要求的"去掉首尾空白"，改为 `email.strip().lower()`，这样 `" A@X.com "` 与 `"a@x.com"` 才能匹配上。
- `normalize_phone` 已符合文档，未改动。

## 验证结果
- 传递链 `A(邮箱)-B(邮箱/电话)-C(电话)` 正确合并为 `[2,5,9]`；空值不参与匹配；无重复返回 `[]`。
- 20 万条：
  - 每 4 条一组（5 万个组）：**0.395s**
  - 全部唯一：**0.323s**
  - 全体共享一个邮箱（单个 20 万大组）：**0.301s**

均远低于 3 秒要求。临时测试脚本已删除。
