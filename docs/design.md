# 架构与设计决策

## 架构

```
用户输入
   │
   ▼
┌───────────────────────── Agent 循环 (agent.py) ─────────────────────────┐
│  messages ──► LLM (llm.py) ──► 有 tool_calls？ ──否──► 输出回答，结束        │
│      ▲                              │是                                  │
│      │                              ▼                                    │
│      │                   解析参数 → 预检 → 权限确认 (permissions.py)          │
│      │                              │                                    │
│      │                              ▼                                    │
│      └──── 工具结果（截断后）◄── 执行工具 (tools/)                           │
└──────────────────────────────────────────────────────────────────────────┘
                                      │
                       所有路径经过 Workspace 沙箱校验 (workspace.py)
```

| 模块 | 职责 |
|---|---|
| `agent.py` | 核心循环、system prompt、错误处理、中断后修复历史 |
| `llm.py` | 模型调用与 token 统计 |
| `tools/` | `list_dir` `read_file` `grep` `write_file` `edit_file` `run_command`；后台进程 `start_process` `process_output` `stop_process` `list_processes` |
| `permissions.py` | 逐个确认 / 本会话总是允许 / 命令前缀白名单 / 自动模式 |
| `checkpoints.py` | 每轮的检查点：写文件前备份原样，撤销时恢复 |
| `shadow.py` | 沙箱的工作区副本：复制项目、对比改动、应用（冲突检测）、放弃、同步用户的修改 |
| `sandbox.py` | Docker 沙箱：常驻容器、docker exec 执行、临时联网、容器内整组终止进程、残留容器清理；镜像定义在 `coder/sandbox_image/Dockerfile` |
| `redact.py` | 工具结果发给模型前遮蔽密钥，阻止把占位符写回文件 |
| `web/guard.py` | 网页访问控制：访问令牌、Origin / Host 检查 |
| `portforward.py` | 沙箱端口预览：发现容器里的监听端口，经 docker exec 转发到本机 |
| `mcp.py` | MCP 客户端：stdio / Streamable HTTP 传输、握手、分页列工具、调用、服务器反向请求，把 MCP 工具包装成 agent 的工具 |
| `swebench.py` | SWE-bench Lite 子集：克隆仓库、沙箱里建环境、套官方测试补丁判分、导出补丁 |
| `workspace.py` | 路径沙箱，禁止访问工作区以外的文件 |
| `ui.py` | 终端输出，与逻辑解耦 |
| `web/` | 浏览器界面：`session.py` 管理对话和浏览器连接、在后台线程跑 agent 并转成事件；`server.py` 提供 HTTP + WebSocket；`static/` 纯 HTML/JS 前端 |
| `store.py` | 对话历史、图片和最近工作区的本地持久化（`~/.coder/`） |
| `context.py` | 上下文管理：token 估算、裁剪早期工具输出和写文件的大段内容、压缩成摘要 |
| `providers.py` | 服务商预设：默认接口地址和常用模型（给设置界面用） |
| `team_roles.py` | 团队模式的岗位预设：测试、安全审查（固定出场）和前端、后端等开发岗位的职责说明、数量规则 |
| `memory.py` | 团队模式的项目记忆：需求索引、模块卡片（ast 提取接口）、黑板持久化、主 agent 的记忆总览 |
| `team.py` | 团队模式：主 agent 的 `plan_tasks` / `dispatch` 工具（后台运行，完成后把汇报送给主 agent）、子 agent 的 `complete_task` 交付检查、共享黑板、文件归属检查、返工通知下游、操作日志 |
| `eval.py` | 评测运行器：隔离工作区、隐藏测试判分、结果统计与轨迹保存 |
| `demo.py` | 演示用的脚本化假模型 |

Web 界面的数据流：

```
浏览器 ◄──WebSocket 事件──  WebSession  ◄── WebUI（和 ConsoleUI 同一套接口）◄── Agent 线程
       ──用户消息/权限回应/停止──►      └─► 权限请求：Agent 线程阻塞等待浏览器回应
```

Agent 本身完全不知道界面是终端还是网页，只调用 `ui.tool_call()`、`ui.ask_permission()` 这类接口，换界面不用改 agent。

## 关键设计决策

**1. 用精确替换而不是整文件重写来改代码**
`edit_file` 要求模型给出 `old_string → new_string`，且 `old_string` 在文件中必须唯一。好处有三点：输出 token 少很多；不会误改没提到的代码；匹配失败时能给出明确的错误，让模型重新读文件再试。Claude Code 的 Edit 工具也是这种设计。

**2. 错误也是一种观察结果**
工具报错（文件不存在、参数 JSON 不合法、匹配不唯一、命令超时）不会让程序崩溃，而是作为工具结果交还给模型。错误信息里写清楚"下一步该怎么做"，模型就能自我纠正。

**3. 权限确认时展示 diff，拒绝时可以给反馈**
写操作会先预检，再展示 diff 请用户确认。参数有问题时直接报错给模型，不打扰用户。用户拒绝时可以附一句理由，比如"文件名改成 b.py"，理由会回传给模型，让它调整做法，而不是重复尝试同一件事。

**4. 工具输出截断保留头尾**
测试日志的报错通常在末尾，开头则是上下文，所以截断时保留两头、去掉中间。

**5. 中断后修复对话历史**
OpenAI 协议要求每个 `tool_call` 都必须有对应的 tool 结果。按 Ctrl+C 中断后，程序会补上"用户中断了执行"的结果，保证对话还能继续。

**6. 界面和 agent 解耦，事件可重放**
Web 界面把 agent 的每个动作变成事件推送给浏览器，并在服务端保留事件日志。刷新页面或断线重连后，日志会完整重放，界面恢复原样。停止任务采用"协作式取消"：在下一次调用模型或执行工具之前检查停止标志，不会强杀线程，所以对话历史始终保持合法。

**7. 流式输出与思考内容回传**
模型输出按片段推送到界面，思考过程和回复逐字显示；工具调用的参数也是分片到达的，由 `llm.py` 按 index 拼装完整。停止检查放在每个片段的回调里，所以生成到一半也能立即停下。对于带思考能力的模型，同一轮工具调用中把 `reasoning_content` 回传给模型，保证推理连贯；用户开始新一轮提问时再丢弃旧的思考内容，节省 token。

**8. 图片按内容寻址存储**
图片按 OpenAI 多模态格式（`image_url` + base64 data URL）和文字一起发给模型。落盘时以 SHA-256 哈希命名存到 `~/.coder/images/`，对话文件和界面事件里只保存引用（`coder-image:<id>`），加载对话时再还原。同一张图只存一份，对话 JSON 不会被 base64 撑大。前端在发送前把大图缩到长边 2000 像素，并统一转成 PNG/JPEG。

**9. 项目说明文件**
工作区根目录下的 `AGENT.md` 会自动注入 system prompt（相当于 Claude Code 的 `CLAUDE.md`），可以写项目约定、测试命令等。

**10. 两级上下文压缩**
每次调用模型前估算上下文大小：以上一次请求的**实际** token 数为基准，加上之后新增消息的估算值（英文约 4 字符/token，中文约 1 字/token，图片按固定值）。超过阈值时：
- 第一步，把较早的长工具输出（读文件、运行日志）裁剪成开头一小段，并注明"需要的话请重新读取"。这类内容占上下文大头、过后可以重新获取，裁剪几乎没有信息损失，也不用额外调用模型
- 第二步，还是太长，就把早期对话转成纯文本记录，让模型写一份结构化摘要（用户要求、改过的文件、命令结果、当前进度），替换掉早期消息。切分点只落在 user/assistant 消息上，保证 tool 调用和它的结果不会被拆开

Web 界面的历史记录不受影响，用户仍然能看到完整过程；压缩只影响发给模型的内容。

**11. 先读后改**
工作区记录 agent 读过（或自己写过）的每个文件当时的修改时间。修改已有文件前检查：没读过的拒绝（防止凭猜测改代码），读过但之后被命令或用户改动的也拒绝（防止基于过期内容修改，覆盖别人的改动），错误信息会告诉模型去重新读取。

**12. 评测集也要被测试**
评测分数只有在测试本身正确时才有意义。每个任务都带参考答案，`--validate` 检查两件事：初始代码**不能**通过隐藏测试（否则任务形同虚设），参考答案**必须**通过（否则测试写错了）。隐藏测试在 agent 完成之后才复制进工作区，避免 agent 针对测试作弊。

**13. 压缩的改进：先无损，摘要里的关键事实不经过模型转述**
压力测试暴露了"压缩 → 重读 → 再压缩"的循环。v2.0 的改法：
- 早期 `write_file` / `edit_file` 调用参数里的大段代码换成一行占位说明（内容已经在磁盘上，需要时重新读取）。大任务里助手消息占了输入的 70%，主要就是这些
- 估算时把工具定义和系统提示这些固定开销算进预算，并用上一次请求的实际 token 数校准估算值；压缩目标是降到阈值的 60%，留出余量
- 两次摘要之间至少间隔 4 次模型调用。刚压缩过还超，就只做无损裁剪，宁可暂时超出预算，也不连续调用模型写摘要
- 用户本轮的原始要求和本次改过的文件清单由程序直接写进摘要。多次压缩后，"摘要的摘要"会逐渐失真，这两项最不能错
- 摘要要求单独保留"工作集"：继续工作必须知道的规则、接口、数据格式和边界情况，原样保留，不能概括成"按需求实现"

**14. 团队模式：用共享黑板代替子 agent 之间的对话**
子 agent 之间不能直接对话。如果让它们自由交流，流程不可控、成本也难以预测。这里借鉴 LangGraph 的中央 state，用一块黑板保持一致：
- **契约单写者**：模块之间的接口由主 agent 写；修改已有契约只能由负责人或主 agent 进行，其他人只能留言提问
- **决策只追加**：子 agent 用 `board_post(kind="decision")` 记录别人可能依赖的实现决定，不能修改或删除
- **文件归属**：每个文件只属于一个任务，写别人的文件会被拒绝，错误信息会说明属于谁、怎么沟通。验收测试属于主 agent，子 agent 改不了，测试标准不会被悄悄放宽
- **增量推送**：每个 agent 每一步执行完工具后，黑板上新出现的、和它相关的内容自动附在工具结果后面；新派出的子 agent 在任务说明里拿到已有的契约和决策。不需要 agent 记得去查
- **返工保留上下文**：主 agent 把任务退回时，用的还是原来那个子 agent，它记得自己做过什么
- **小任务不拆**：要不要拆由主 agent 判断；对比实验表明上下文够用时拆分只增加成本
- 子 agent 并行写文件，没有统一的对话记录，所以团队把所有成功的写文件、改文件、运行命令按时间顺序记进操作日志，`coder.replay` 按它还原交付的代码

**15. 项目记忆：主 agent 看摘要，子 agent 拿完整的任务上下文**
项目大了以后，主 agent 不可能把需求、所有代码和测试同时放在上下文里；压缩之后再把整个项目重读一遍，又会马上超出预算。所以把全局信息存在工作区的 `.coder/memory/` 里（`memory.json` 给程序，`MEMORY.md` 给人看），而不是放在上下文里：
- **需求索引**：按标题把需求文档切成带编号的小节（S1、S2……），原文一字不改。拆任务时给每个任务指定它实现哪些小节，子 agent 拿到这些小节的**原文全文**
- **模块卡片**：每个代码文件一张卡，对外接口（类、函数签名）和项目内依赖由程序从代码里提取（ast），不经过模型转述；说明取自模块开头的文档字符串。子 agent 拿到所依赖模块的**接口卡片**，不拿实现代码
- **黑板**：契约、决策、任务状态，每次变化都写进文件
- **主 agent** 平时看记忆总览（需求目录 + 契约 + 任务 + 所有卡片），需要细节时用 `spec_section` 读需求原文、`read_file` 读代码；**上下文被压缩时，总览由程序原样写进摘要**，不用把整个项目重读一遍
- **验收测试也拆出去**：由专门的子任务按模块写（严格依据需求小节和契约），实现任务依赖它，实现者拿测试自测
- 能由程序提取的一律程序提取；模型写的内容（文档字符串）只当目录用，原文永远以文件为准，改代码前仍然要先读真实文件
- 没有用向量检索（RAG）：需求有编号、代码有模块和接口，按结构精确取比按相似度模糊取更可靠，也不需要随代码变化维护向量索引。项目大到按结构也找不到东西时，再考虑加检索

**16. 子 agent 按岗位分工：固定的质量岗位 + 按项目选的开发岗位**
- **测试和安全审查是固定岗位，团队模式下总是出场**：写代码的人不应该自己给自己验收。测试岗位根据需求写验收测试（实现者依赖它、用它自测，改不了它），实现完成后再派它运行全部测试、汇报失败，主 agent 不用自己读大段测试日志。安全审查只读，发现的问题交给主 agent，由文件的负责人修，职责清楚，也不会和实现者改同一个文件
- **由程序保证出场**：主 agent 结束时如果写过代码、却还没派出过测试或安全审查，会收到一次提醒，补上后再结束
- **开发岗位按项目类型选**：前端、后端、数据库、命令行和工具库、文档各有专门的职责说明（比如前端要转义渲染的数据、后端要在边界校验输入、数据库要用参数化查询）。不是所有项目都有前后端，所以岗位由主 agent 按项目选；项目大时同一个岗位开多个，按模块再分
- **数量有规则、有上限**：试跑中曾经出现一个模块配一个写测试的子 agent（8 个），成本大部分花在写测试上。现在按实现任务的数量配比，各最多 3 个

**17. 后台进程、命令白名单和撤销**
- **后台进程**：`run_command` 要等命令结束，开发服务器只能等到超时。现在 `start_process` 在后台启动，可以等到输出里出现指定内容（如 `listening`）再返回；`process_output` 只返回上次之后的新输出，不重复占上下文。用 `shell=True` 启动时，真正的程序是 shell 的子进程，只杀 shell 会留下孤儿进程，还占着输出管道让工具一直卡住（`run_command` 超时时以前就会这样），所以启动时让命令自成进程组，停止时整组终止（Windows 用 `taskkill /T`）。切换对话、`/reset`、退出程序时全部终止
- **命令白名单按前缀**："本对话总是允许 run_command"太粗，等于允许任何命令。现在可以只允许某类命令，前缀按程序取：`python -m pytest -q` 取 `python -m pytest`，`git status -s` 取 `git status`；解释器（python、node、bash 等）必须带上脚本名，`python app.py` 取 `python app.py`，`python -c ...` 不提供这个选项，因为只允许 `python` 等于允许任意代码。带 `&&`、`;`、`|`、重定向、`$( )` 的命令不按白名单放行，防止在允许的命令后面夹带别的命令
- **撤销用检查点，不用 git**：用户的项目不一定是 git 仓库，也不该替用户提交。每轮开始建一个检查点，agent 第一次写某个文件之前备份原样；撤销时恢复，新建的删除。撤销前比对每个文件当前的内容和 agent 最后写完时是否一致，不一致说明之后被人或命令改过，先提示，不悄悄覆盖。撤销后下一轮告诉模型哪些文件被恢复了；先读后改的机制会发现文件变了，要求重新读取。团队模式里一轮任务所有 agent 的修改算一个检查点

**18. Docker 沙箱：常驻容器 + 按需联网**
- **每个会话一个常驻容器**，命令用 `docker exec` 执行，而不是每条命令新建容器：省掉一两秒的启动时间，也保留了命令之间的状态（装好的依赖、生成的文件）
- **默认断网，按命令申请**：命令带上 `network: true` 才临时接入网络，执行完断开。联网的确认绕不过去：自动模式、"总是允许"、命令白名单都不算数，因为提示注入最危险的后果就是被诱导把代码或密钥发出去。实现上用默认网络启动容器再断开（`--network none` 的容器之后接不上网络）
- **在容器里终止整组进程**：只杀掉本机的 `docker exec` 客户端，容器里的进程还会继续运行（试过）。所以每条命令用 `setsid` 自成进程组、记下组号，停止时在容器里整组终止；加 `--init` 回收僵尸进程
- **不留残留容器**：正常退出时删除；被直接结束（关掉终端窗口）来不及清理的，下次启动沙箱时删掉"主人进程已经不在"的容器。退出清理一开始用弱引用登记，对象在 `main()` 返回后先被回收，结果容器没删掉，改成强引用并补了回归测试
- **一个通用镜像**：Python、Node.js、git、编译工具一次装齐（约 600MB），避免遇到新项目就换镜像；Dockerfile 跟着项目走，基础镜像固定版本

**19. 网页防跨站控制、遮蔽密钥**
- 服务只监听 127.0.0.1，但挡不住用户正在浏览的其他网站：浏览器不限制网页连接 `ws://127.0.0.1`，恶意网页可以连上来布置任务，开着自动模式就等于远程执行命令；DNS 重绑定还能绕过同源限制读写接口。现在三道检查：Host 必须是本机地址（挡 DNS 重绑定），带 Origin 的请求必须来自本服务的页面（挡跨站 WebSocket），每个请求都要带访问令牌。令牌放在启动链接里，第一次访问换成 `HttpOnly; SameSite=Strict` 的 Cookie，别的网站发起的请求不会带上它
- 工具结果（读到的文件、命令输出）会原样发给模型服务商。发送前把高可信度的密钥格式（`sk-…`、`ghp_…`、`AKIA…`、私钥块、JWT 等）和像密钥的赋值换成占位符，界面和对话记录里也只有占位符。规则宁可漏掉也不误伤：在项目自己的代码和 1861 个第三方库文件上检查，只命中了文档里的示例密码
- 占位符绝不能写回文件，否则真正的密钥会被覆盖：写文件、改文件的参数里出现占位符时直接拒绝，提示模型只改不含密钥的部分

**20. 多模型兼容：按服务商的差异做容错，而不是写死某一家**
- 同样是"OpenAI 兼容"，各家细节不同：有的模型只接受默认的 `temperature`，缓存命中的字段名不同，思考内容有的在 `reasoning_content`、有的用 `<think>` 写在正文里。都在 `llm.py` 里统一处理，agent 循环不需要知道是哪一家
- 正文里的 `<think>` 只在显示时分开，发回给模型的历史保持原样：这类模型的官方建议是多轮工具调用时保留思考内容，改写历史可能影响它的表现
- **回复被截断不等于完成**：没有工具调用的回复以前一律当成"任务完成"。GLM 一次回复写了 25 万字符的思考、撞上 65536 token 的输出上限，正文和工具调用都没有，任务就这样结束了。现在记录每次回复的结束原因，`length` 时提醒模型继续、把回复写短、大文件分段写，同一轮最多提醒 3 次

**21. SWE-bench：在真实项目上判分，环境放进沙箱**
- 自写任务规格清楚，外部的公认题目更有说服力。SWE-bench 的环境搭建是难点：每道题要对应版本的 Python 和固定版本的依赖。这里选了依赖轻、测试不需要联网的项目，环境在 Docker 沙箱里用 uv 建，每个"项目 + 版本"一个虚拟环境放在持久卷里复用
- 测试补丁在 agent 做完之后才放进工作区；判分前把测试文件恢复成出题时的样子，agent 自己新建的同名文件先删掉（试跑时 agent 为验证修复新建了测试数据文件，和官方补丁冲突）
- 先用官方答案校验每道题的环境（不打补丁时相关测试失败、打上后全部通过），再拿来评 agent：环境问题和模型问题分开

**22. MCP：自己实现客户端，能力做成所有 agent 共用的本地中枢**
- 客户端自己实现 JSON-RPC：stdio 传输一行一条消息，读写各一个线程，响应按 id 交给等待的请求；Streamable HTTP 的响应可能是 JSON，也可能是 SSE 流，两种都处理，并带上服务器给的会话编号。服务器反过来发的请求（问工作区在哪）由客户端回答
- 工具名统一成 `mcp__服务器名__工具名`，并按 OpenAI 函数名的规则清洗（只能是字母、数字、`_`、`-`，最长 64）；工具参数的 JSON Schema 去掉 `$schema` 再交给模型
- 图片结果存成文件、结果里写路径，不直接塞给模型：不是所有模型都能看图（DeepSeek V4 Flash 就不能），Playwright 也会返回文字形式的页面结构
- 联网、搜索、浏览器这些能力不放进 Coding-agent，而是交给独立的本地 MCP 中枢：几个 agent 共用一套服务器和一份配置，浏览器这种有状态的给每个会话单独一份。通用的事情做成本地服务，项目里不重复开发

**23. 参考 11 个开源编码 agent 的源码，重构可靠性和团队调度**
2026 年的源码研究《Harness Engineering》对比了 Claude Code、Codex CLI、Gemini CLI、OpenHands、Aider、OpenCode、Pi、Hermes 等 11 个 agent。对照下来，Coding-agent 的问题大多已经有成熟的解法，这一版逐条借鉴：
- **工具调用格式错误不能让对话报废**：参数不是合法 JSON 时，原样放回历史会让下一次调用被服务商整个拒绝（400）。现在历史里换成合法的空参数、不执行并让模型重来（和同一作者的 OPC 遇到的是同一个问题）。回复被输出上限截断时，这条消息里的工具调用一律不执行：补出来的参数可能能通过校验，内容却不完整（参考 Pi）。连续 3 步格式错误就停下（参考 Mini-SWE-Agent）
- **"完成"不能只靠模型自己说**：单 agent 用 verify-on-stop（参考 Hermes）：改了代码、之后没有成功运行过验证命令就想结束时否决一次，让它去验证或说明为什么没法验证；只改文档不要求。子 agent 用 `complete_task` 交付（参考 Gemini CLI 的子 agent）：纯文字回复不算交付，系统检查负责的文件、Python 语法、改了代码之后有没有验证过，不通过退回给它自己改，提交 3 次还不过就带着问题交给主 agent；步数用完时给一次只能交付的收尾回合
- **派发不阻塞**：以前 `dispatch` 要等这一批子 agent 全部做完才返回，依赖早做完任务的任务也要等最慢的那个，子 agent 在黑板上的提问也要等整批结束主 agent 才看得到。现在子 agent 在后台运行，每个做完汇报就在主 agent 的下一步送到（参考 Hermes、OpenCode、Codex 的后台子 agent）；主 agent 没事可做时结束这一步，系统等下一个汇报。主 agent 不能改正在运行的子任务负责的文件
- **运行中可以插话**（参考 Pi 的 steer 队列）：用户的话排队，在当前这一步的工具执行完后插入对话，不打断正在进行的调用；agent 想结束时刚好有插话，也先处理。团队模式交给主 agent
- **循环检测**：除了连续 3 次完全相同的调用，还检测两三个调用组成的循环（A-B-A-B 重复 3 次）和同一个调用反复失败（参考 Gemini CLI、OpenHands 的卡住检测）
- **上游返工通知下游**：返工改了文件时，依赖它、已经完成的任务和主 agent 都收到通知，由主 agent 决定要不要重新派发
- **提示词分层**：写验收测试的规则只放在测试岗位的职责里，通用的子 agent 提示词里只有交付方式
