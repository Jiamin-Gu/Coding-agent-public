# 评测

## 评测方法与结果

```bash
python -m coder.eval              # 跑全部任务（默认 4 个并行）
python -m coder.eval --tasks bug  # 只跑名字包含 bug 的任务
python -m coder.eval --repeat 3   # 每个任务跑 3 次，看稳定性
python -m coder.eval --validate   # 不调用模型，用参考答案校验评测集本身
python -m coder.analyze evals/results/<某次评测的目录>   # 分析 token 账本
python -m coder.replay evals/results/<某次评测的目录>    # 从轨迹重放出 agent 交付的代码，整理成示例
python -m coder.eval --verbose     # 实时打印每个任务的每一步，适合盯长任务
python -m coder.eval --team        # 团队模式（--team always 强制拆分）
python -m coder.eval --sandbox     # agent 的命令在 Docker 沙箱里执行

# SWE-bench Lite 子集（需要 Docker；第一次会克隆 pytest、flask 仓库并在沙箱里建环境，约下载 170MB）
python -m coder.swebench fetch               # 下载选定的 10 道题
python -m coder.swebench validate            # 用官方答案校验环境
python -m coder.swebench run --model deepseek-v4-flash
python -m coder.swebench export evals/results/<目录>...   # 把各模型交出的补丁整理成示例
```

每个任务在独立的临时目录里运行（自动模式），完成后才把**隐藏测试**放进工作区，用 pytest 判分。结果表和每个任务的完整对话轨迹保存在 `evals/results/`，用于分析失败原因。还可以用 `--no-read-guard`、`--no-compact` 做消融对比。

任务放在 `evals/tasks/<任务名>/`：`prompt.md`（任务描述）、`setup/`（初始代码）、`tests/`（隐藏测试）、`solution/`（参考答案，只用于校验）。新增任务后先跑一次 `--validate`，确认初始代码不通过、参考答案通过。任务名的前缀就是类型（`algo_`、`bug_`、`feature_`、`refactor_`、`multi_`、`debug_`、`long_`），报告会按类型统计。

`--tasks` 支持用逗号同时指定多个，例如 `--tasks multi_,debug_`。任务目录里可以放 `task.json` 单独配置，例如大任务需要更多步数：`{"max_steps": 80}`；非 Python 任务指定判分命令：`{"test_command": ["node", "--test", "{tests}/*.test.mjs"]}`。

**重放成果**：评测时每个任务在临时目录里运行，跑完就删除；`python -m coder.replay` 从轨迹里按顺序重新执行 agent 成功的写文件、改文件和删除临时文件的命令，还原出它交付的代码，再用隐藏测试复验，并为每个任务生成说明（任务、成本、改了哪些文件、agent 的总结）。

**token 账本**：每次运行的轨迹文件里有 `call_log`，记录每次调用模型的输入、缓存命中、输出，以及上下文里系统提示、工具定义、用户消息、助手消息、工具结果各占多少。`python -m coder.analyze` 汇总成报告：上下文构成、每一步的输入大小、重复读取文件和重复执行命令的次数、通过与失败运行的成本对比。

**费用换算（可选）**：在 `.env` 里填每百万 token 的价格，报告会把 token 换算成费用：

```
CODER_PRICE_INPUT=未命中缓存的输入价格
CODER_PRICE_CACHED=命中缓存的输入价格
CODER_PRICE_OUTPUT=输出价格
```

#### 当前基线（v1.1.0，deepseek-flash，17 个任务 × 3 次）

| 指标 | 结果 |
|---|---|
| 通过率 | **51/51（100%）**，7 类任务全部通过 |
| 平均每次运行 | 调用模型 8.7 次，耗时 19 秒 |
| 平均每次运行的 token | 输入 39,276（命中缓存 90%），输出 3,891 |
| 单次调用的最大输入 | 17,673 token（从未触发上下文压缩） |
| 输入构成 | 助手消息 46%（主要是写文件时的代码内容）、工具定义 22%、工具结果 18%、系统提示 9%、任务描述 4% |
| 可能的浪费 | 51 次运行中重复读取 7 次、重复执行相同命令 11 次（其中一部分是改代码后重跑测试，属于必要） |

解读：在这个规模的任务上，缓存命中率已经很高、浪费很少；没有命中缓存的输入只有约 19 万 token，和输出（约 20 万 token）差不多，而输出通常更贵，所以**输出是主要成本**。另外，单次调用的上下文最多不到 2 万 token，压缩机制完全没有被这些任务测到。

#### 压力测试：压缩会不会让 agent 记错？（7 个困难任务 × 3 次，压缩阈值 8000 token）

为了测试上下文压缩对质量的影响，把阈值从默认的 6 万降到 8000，逼 agent 频繁压缩，再和基线对比：

| 指标 | 基线（不触发压缩） | 压力测试 |
|---|---|---|
| 通过率 | 21/21 | **21/21**（压缩过的 10 次运行全部通过） |
| 压缩次数 | 0 | 48 次（`long_spec_textkit` 平均每次运行 12.7 次） |
| 压缩后的"凭记忆操作"错误 | — | **0**（没有出现没读就改、替换不存在的文本） |
| 输入 token | 130 万（命中缓存 92%） | 159 万（命中缓存 **68%**） |
| 未命中缓存的输入 | 10 万 | **51 万（约 5 倍）** |
| 输出 token | 14 万 | **42 万（约 3 倍）** |

结论：
- **质量守住了**：摘要加上"先读后改"约束，压缩后没有出现凭记忆修改文件的错误，也没有因此失败
- **但频繁压缩会显著增加成本**：每次压缩都要额外调用一次模型写摘要，还会让缓存失效；压缩后 agent 需要重新读取文件，又很快超过阈值，形成"压缩 → 重读 → 再压缩"的循环。`long_spec_textkit` 从第 10 步开始基本都在重读和重跑，最后撞上 30 步上限（这次仍然通过，但更难的任务可能因此做不完）
- **启示**：压缩只能作为很少触发的兜底，不能当成省钱手段。上下文预算必须装得下任务的"工作集"（需要反复查看的规格和代码），否则会陷入循环

**v2.0 改进压缩后，同样的压力测试：**

| 指标 | v1.1 | v2.0 |
|---|---|---|
| 通过率 | 21/21 | 20/21（失败的一次见下） |
| 压缩次数 | 48 | **29（-40%）** |
| 未命中缓存的输入 | 51.2 万 | **41.4 万（-19%）** |
| 输出 | 41.8 万 | **34.0 万（-19%）** |
| 平均耗时 | 91 秒 | 75 秒 |

失败的一次是 `long_spec_textkit`：30 步上限内没有做完（还没写测试和运行测试），不是压缩后记错了东西。这个任务在 8000 预算下两个版本都每次跑满 30 步，处在做得完和做不完的边缘。为了确认，又单独补跑了 6 次，6/6 通过，v2.0 合计 8/9。

#### 大任务基线（deepseek-flash，2 个任务 × 3 次）

| 任务 | 通过 | 模型调用 | 输入 tokens（缓存命中） | 输出 tokens | 耗时 |
|---|---|---|---|---|---|
| `large_build_ledger`（照需求文档从零实现记账工具） | 3/3 | 22 | 56.4 万（99%） | 3.2 万 | 150 秒 |
| `large_library_softdelete`（44 个文件的系统里加软删除和审计） | 3/3 | 21 | 34.1 万（96%） | 1.2 万 | 62 秒 |

单次调用的上下文最多约 3 万 token，没有触发压缩。也就是说，以 `deepseek-flash` 的能力和默认 6 万的预算，这两个"大任务"单个 agent 就能稳定完成。

#### 单 agent vs 团队模式

| 条件 | 通过 | 平均模型调用 | 平均输入 / 输出 tokens | 平均耗时 |
|---|---|---|---|---|
| 单 agent（默认预算） | 6/6 | 21 | 45 万 / 2.2 万 | 106 秒 |
| 团队模式 auto（主 agent 自己判断） | 2/2 | 18 | 38 万 / 2.2 万 | 105 秒 |
| 团队模式 always（强制拆分） | 2/2 | 62 | 130 万 / 5.4 万 | 292 秒 |
结论：
- **auto 模式的判断是对的**：两个任务主 agent 都选择自己完成，结果和成本与单 agent 一样，没有因为多了团队能力而变差
- **任务不够大时，拆分是纯开销**：强制拆分仍然全部通过，但 token 约 3 倍、耗时约 2.8 倍。子 agent 各自要重新探索代码，主 agent 要写契约、验收测试并协调，这些都是额外成本；DeepSeek 的并行请求也没有缩短总时间
- **协作机制本身是有效的**：强制拆分的运行里，子 agent 没有越权写别人的文件，接口靠契约对齐；`repos` 子 agent 发现主 agent 写的验收测试要求"所有实体 id 全局唯一"，与自己的实现冲突，核实后按测试修正，并把决定记到了黑板上（见 [examples/team](../examples/team/README.md)）
- **还没有验证的，也是团队模式真正要解决的问题**：项目复杂到单个 agent 要同时记住太多模块时，注意力会分散。把子任务连同它需要的全部上下文交给子 agent，主 agent 只统筹契约和汇报，能不能做得更好。这需要一个真正复杂的任务来测，现有的两个大任务还不够

#### 更复杂的任务：照需求文档从零实现订单库存系统（v2.1，deepseek-v4-flash）

`large_spec_shop`：214 行的需求文档（商品、库存、阶梯价 / 类别折扣 / 税、优惠券分摊、订单状态流转、报表、持久化），98 个隐藏测试，参考答案 578 行。各方式各跑 1 次（试跑，不是正式评测）：

| 方式 | 隐藏测试 | 模型调用 | 输入 + 输出 tokens | 耗时 | 说明 |
|---|---|---|---|---|---|
| 单 agent | 98/98 | 33 | 127 万 | 312 秒 | 上下文最大 5.7 万，没有压缩 |
| 团队 auto（v2.0） | 98/98 | 134 | 504 万 | 943 秒 | 主 agent 拆成 3 个子 agent |
| 团队 always（v2.0） | 98/98 | 157 | 568 万 | 1211 秒 | 拆成 7 个；主 agent 写的验收测试有 2 处和需求矛盾，靠子 agent 发现、返工 |
| 团队 auto（减少开销后） | 98/98 | 62 | 254 万 | 398 秒 | 主 agent 判断自己做，没拆；收尾时上下文超过 6 万，压缩后重读整个项目 |
| 团队 always（减少开销后） | 98/98 | 125 | 451 万 | 945 秒 | |
| 团队 always（项目记忆） | 98/98 | 141 | 481 万 | 806 秒 | 实现代码的 4 个子 agent 只用了 6～12 次调用、上下文 2.3～4.1 万，没有一次提问或冲突；成本转移到了写验收测试的子 agent |

结论：
- **按任务分配上下文是有效的**：项目记忆版本里，实现者拿到自己的需求小节原文和依赖模块的接口卡片，直接写对，不需要再摸索和沟通
- **但这个任务单个 agent 就装得下**（单 agent 最大上下文 5.7 万），所以团队方式怎么优化都是单 agent 的 2～4 倍成本。要证明团队方式的价值，需要单个 agent 装不下的任务
- **还要解决的**：写验收测试的子 agent 写得过多（每个都接近 6 万上下文）；主 agent 自己的上下文仍会涨到 6 万；上下文贴着压缩阈值时，每一步的无损裁剪都会改动前面的消息，导致缓存失效（一个子 agent 70 万输入没命中缓存），应该一次裁到明显低于阈值

#### 多模型对比（v2.5，单 agent，每个任务 1 次）

同一组 5 个代表性任务，用其他几家的模型驱动（完整记录、失败分析和原始数据见 [evals/reports/2026-10-11-multi-model](../evals/reports/2026-10-11-multi-model/README.md)）：

| 模型 | 通过 | 调试 | 多文件 | 长规格 | 大任务 ledger | 大任务 shop | 调用 | 耗时 |
|---|---|---|---|---|---|---|---|---|
| DeepSeek V4 Flash | **5/5** | ✓ | ✓ | ✓ | ✓ | ✓ | 81 | 15 分钟 |
| Kimi K2.7 Code | 4/5 | ✓ | ✓ | ✓ | ✓ | ✗ 84/98 | 108 | 28 分钟 |
| GLM-5.2 | 4/5 | ✓ | ✓ | ✓ | ✓ | ✗ 被截断 | 71 | 87 分钟 |
| Qwen3.7 Plus | 3/5 | ✗ | ✓ | ✓ | ✗ 25/26 | ✓ | 78 | 33 分钟 |
| MiniMax M3 | 2/5 | ✗ | ✓ | ✓ | ✗ 25/26 | ✗ 交卷太早 | 117 | 20 分钟 |

- 4 家模型都能驱动这个 agent。失败主要来自模型能力：漏看文档里写明的规则（邮箱要去掉空格）、接口和规格对不上
- 发现并修复了 4 个兼容问题：Kimi 只接受 `temperature=1`；各家缓存命中的字段名不同；MiniMax 把思考写在正文的 `<think>` 里；回复撞上输出上限被截断时被当成"完成"（GLM 一次回复写了 25 万字符的思考）。修复后 GLM 重跑 shop：被截断 1 次、提醒后继续，98/98 通过
- 新增的 2 个 JavaScript 任务（异步队列修 bug、Markdown 渲染防 XSS）5 个模型全部通过
- 之后的开发和评测只用 DeepSeek：差异主要是模型能力，而且它的价格最便宜

#### SWE-bench Lite 子集（v2.5）

**DeepSeek V4 Flash：10/10 全部解决**（每道 17～46 次模型调用、15～141 万 token、2～19 分钟）。其他模型的那一轮跑到一半触发了订阅的共享额度上限，是部分结果：

#### 降低团队模式开销的尝试（v2.5，没有效果）

`large_spec_shop` 上团队模式的开销大约是单 agent 的 4 倍。v2.5 试着降低：测试岗位按每 8 个实现任务配 1 个（写在主 agent 的提示词里）、测试和安全审查的步数上限 30 和 20、最后的验收测试由主 agent 自己运行。用 DeepSeek 跑了 1 次：

| | v2.2 岗位版 | v2.5 降开销后 |
|---|---|---|
| 隐藏测试 | 98/98 | 98/98 |
| 模型调用 | 154 | 231 |
| 输入 + 输出 tokens | 543 万 | 1002 万 |
| 耗时 | 1189 秒 | 2805 秒 |

没有效果：主 agent 没有照提示词里的配比，仍然派了 3 个测试岗位；安全审查用满 20 步，仍然发现了问题、交给负责人返工后复查通过；多出来的开销主要在实现子任务上（有的从 7 次调用涨到 24 次）。团队模式不同运行之间本来波动就大（之前几次在 125～172 次调用），1 次运行不足以说明改动的好坏。按"不在没有数据时做有损的优化"的原则，没有继续砍测试岗位，这个问题留到以后。

> **撤回的实验**：曾经把所有 agent（包括子 agent）的上下文预算统一压到 1.2 万来对比，两种方式都失败了。这个设计是错的：团队模式的思路是按任务分配上下文，子任务需要多少就给多少，统一压低预算只会逼每个 agent 反复压缩和重读，既不省钱，也测不到要验证的东西。这组结果不作为结论。
