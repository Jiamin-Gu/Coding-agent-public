# 多模型评测记录（2026-10-11）

coder v2.4.0 → v2.5.0 开发期间，用其他几家的模型驱动同一个 agent，检验"任何 OpenAI 兼容接口都能用"这句话。
所有模型都通过同一个 OpenAI 兼容接口调用，单 agent 模式，每个任务 1 次（样本少，单题的成败有运行波动，看整体趋势）。

结论：**4 家模型都能正常驱动这个 agent**（工具调用、思考内容、缓存统计都兼容）；失败主要来自模型能力差异
（漏看文档里写明的规则、接口和规格对不上），不是 agent 的问题。之后的开发和评测只用 DeepSeek，等 agent 完整后再做多模型测试。

`runs.json` 是这一天所有运行的结果数据（每次运行一行：任务、是否通过、调用次数、token、耗时、判分输出、是否有效）。完整轨迹体积太大，只保存在本地的 `evals/results/`。

## 2. 兼容问题（试跑发现，都已修复）

每个模型先跑 1 个小任务（bug_stats），四家都做对了，但暴露出：

1. **Kimi 只接受 `temperature=1`**，传 0 直接 400。现在被拒绝时自动改成不传（还不行就用 1），并记住
2. **缓存命中的字段名不同**：DeepSeek 用 `prompt_cache_hit_tokens`，其他家用 OpenAI 格式的 `prompt_tokens_details.cached_tokens`，现在两种都认
3. **MiniMax 把思考过程用 `<think>…</think>` 写在正文开头**。现在流式解析时分出来，界面上显示成思考过程；发回给模型的历史保持原样（官方建议多轮工具调用时保留）
4. **回复被输出上限截断时被当成"任务完成"**（见第 4 节 GLM），现在会提醒模型继续并把回复写短，最多 3 次

## 3. 5 个代表性任务

和 v2.2 回归测试同一组任务，方便和 DeepSeek 对比：

| 模型 | 通过 | 调试 dedupe | 多文件 inventory | 长规格 textkit | 大任务 ledger | 大任务 shop | 调用 | 耗时 | 输入 / 缓存 / 输出 |
|---|---|---|---|---|---|---|---|---|---|
| DeepSeek V4 Flash | **5/5** | ✓ | ✓ | ✓ | ✓ | ✓ | 81 | 15 分钟 | — |
| Kimi K2.7 Code | 4/5 | ✓ | ✓ | ✓ | ✓ | ✗ 84/98 | 108 | 28 分钟 | 2.38M / 94% / 88k |
| GLM-5.2 | 4/5 | ✓ | ✓ | ✓ | ✓ | ✗ 被截断 | 71 | 87 分钟 | 3.01M / 89% / 251k |
| Qwen3.7 Plus | 3/5 | ✗ | ✓ | ✓ | ✗ 25/26 | ✓ | 78 | 33 分钟 | 1.62M / 79% / 103k |
| MiniMax M3 | 2/5 | ✗ | ✓ | ✓ | ✗ 25/26 | ✗ 交卷太早 | 117 | 20 分钟 | 2.12M / 95% / 107k |

失败原因（都看过轨迹和判分输出）：

- **Kimi / shop**：`add_coupon` 的参数和规格不一致，一处接口错误让 14 个优惠券测试全部失败
- **GLM / shop**：第 2 次回复写了 25 万字符的思考，撞上 65536 token 的输出上限，正文和工具调用都没有，旧代码当成"完成"，20 分钟一个文件没写
- **Qwen、MiniMax / dedupe**：性能都修好了，但都漏了第二个问题：文档字符串里写明邮箱要去掉首尾空格，它们没对照着查（DeepSeek、Kimi、GLM 都查到了）
- **Qwen / ledger**：撤销功能的一个规则没做对（26 个测试过 25 个）
- **MiniMax / ledger**：导出再导入的往返不一致（26 个过 25 个）
- **MiniMax / shop**：写了 7 万字符的思考后说"现在开始实现 Shop 类"就结束了，没有发出工具调用（当时没记录结束原因，可能是模型自己停了，不一定是截断）

行为特点：GLM 最慢（输出长、生成慢）；Qwen 调用最少（shop 只用 14 次就拿了满分）；MiniMax 调用最多，爱用 `python -c` 反复做小实验；Kimi 稳定但大任务上接口细节出错。

MiniMax 的 task_queue 原判 9/10 失败，失败的断言是"同步抛错的任务被 reject 后，紧接着 `pending` 应该是 0"。
结果交给调用方和内部计数减一谁先谁后，取决于微任务的顺序，规格里没有规定，是测试写得过严。
改成等一轮事件循环再检查后，用轨迹重放还原各模型当时交出的代码重新判分：MiniMax 通过，其他模型结果不变。

## 7. 团队模式试跑（MiniMax，large_spec_shop）

| | 单 agent | 团队模式 |
|---|---|---|
| 结果 | ✗（交卷太早）/ ✓ 98/98（重跑） | ✗ 97/98 |
| 调用 | 9 / 88 | 347（主 agent 131，安全审查 56，4 个实现子 agent 各 40 左右） |
| token | 11 万 / 615 万 | 2541 万 |
| 耗时 | 2.5 / 16.5 分钟 | 56 分钟 |

流程是完整的（测试岗位写验收测试 → 实现 → 漏派安全审查被提醒后补上）。但子 agent 一半以上步数在用 `python -c` 做小实验，
40 步上限用完时任务没做完，主 agent 只好自己写代码（写文件、改文件 41 次），开销远超 DeepSeek 的团队运行（154 次调用、543 万 token、98/98）。
这次试跑也把共享额度打到了上限，原定"3 个模型 × 3 次团队模式"的对比没有继续，改为之后只用 DeepSeek 做团队模式实验。

## 8. 额度

所用订阅的额度是**所有模型共享的一个池子**：每个模型列出的"月度上限"只决定它的用量按什么比例折算进总额度
（占比 = 按该模型价格算出的花费 ÷ 该模型的月度上限）。上限：5 小时 20%、每周 50%、每月 100%，触顶后所有模型同时返回 429。

这一天合计约占月度总额度的 23%：GLM 8.8%、MiniMax 5.6%（其中团队试跑一次 2541 万 token）、Kimi 4.2%、DeepSeek 3.1%、Qwen 1.2%。
DeepSeek 按占比是最便宜的（缓存命中 $0.003/百万），大规模、重复的实验优先用它。

## 9. 之后做多模型测试的建议

- 跑之前按"占共享额度的比例"估算，一个模型一个模型地跑，不要并行把几个模型一起跑
- 先补完 SWE-bench 剩下的题，再看各模型在真实项目上的差距
- GLM 思考很长、输出贵，适合少量高难度任务；MiniMax 便宜但调用多，适合大批量的小任务
- 团队模式对弱一些的模型开销会急剧放大，先限制子 agent 的实验性命令和主 agent 的调度轮数，再拿它们做对比
